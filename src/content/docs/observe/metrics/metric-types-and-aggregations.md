---
title: "Metric types and aggregations"
---

The Observability module supports different metric types to represent and visualize telemetry data collected from infrastructure, applications, databases, networks, and messaging systems. Each metric type uses a specific aggregation behavior that determines how data is collected, calculated, and displayed in the Metrics dashboard.

### Metric types and graph types

APIwiz maps each metric type to a specific graph type based on its aggregation behavior. The following table summarizes the metric types, aggregation behavior, and graph types:

### Counter

A counter tracks a cumulative numerical value that continuously increases over time. The value resets to zero when the monitored process restarts. Counters always increase and never decrease during the lifetime of a process, making them reliable for tracking total event counts across a system.

- **Metric data type:** Sum
- **Behavior:** Monotonic
- **Graph type:** Line chart

The line chart makes it easy to visualize the rate of increase over time and identify sudden spikes or drops in event frequency.

Use counter metrics to monitor the following:

- Event frequency and throughput
- Long-term usage trends
- Request and error rate patterns
- Total activity across services over a time period

**Examples:**

- Total requests received by a server over a period of time
- Total API calls processed
- Total messages consumed from a queue
- Total errors generated by an application
- Total number of database transactions committed

### Gauge

A gauge tracks a numerical value that can increase or decrease at any time. Gauges measure the current state of a resource or system component at a specific point in time. Unlike counters, gauges don't accumulate values; they reflect the real-time state of a metric at the moment of collection.

- **Metric data type:** Gauge
- **Behavior:** Non-monotonic
- **Graph type:** Gauge chart

The gauge chart provides an instant snapshot of the current value, making it easy to assess whether a resource is within acceptable thresholds at any given moment.

Use gauge metrics to monitor the following:

- Current resource utilization levels
- Real-time system health indicators
- Instantaneous performance values
- Resource availability at a specific point in time

**Examples:**

- CPU utilization
- Memory usage
- Active database connections
- Queue depth
- Disk usage
- Number of active threads in an application
- Current heap memory usage in a JVM

### Histogram

A histogram measures the distribution of a set of values across predefined ranges, also called buckets. Histograms analyze performance-related metrics and show how values are distributed over time. Instead of showing a single value, a histogram groups multiple observations into ranges to reveal patterns such as latency distribution or response time spread.

- **Metric data type:** Histogram
- **Behavior:** Distribution-based
- **Graph type:** Histogram chart

The histogram chart makes it easy to identify how frequently values fall within specific ranges, helping you detect performance anomalies and understand service-level behavior over time.

Use histogram metrics to monitor the following:

- Response time and latency distribution
- Performance bottleneck identification
- Service-level trend analysis
- Request duration patterns across services
- Distribution of resource consumption over time

**Examples:**

- API response times
- Database query execution times
- Request processing duration
- Message processing latency
- File upload and download durations
- Time taken to complete background jobs

### Bar chart

A bar chart visualizes metrics that use a sum aggregation with non-monotonic behavior. Bar charts compare metric values across multiple categories, resources, or time periods simultaneously. Unlike line charts that show trends over time, bar charts focus on comparative analysis across different entities at a specific point in time.

- **Metric data type:** Sum
- **Behavior:** Non-monotonic
- **Graph type:** Bar chart

The bar chart makes it easy to compare values side by side and quickly identify which resource, service, or component consumes the most or least of a given metric.

Use bar charts to monitor the following:

- Comparative resource utilization across multiple components
- Relative performance differences between services
- Metric value distribution across environments
- Anomalies and outliers across monitored resources

**Examples:**

- CPU utilization across multiple servers
- Memory usage across Kubernetes nodes
- Database connection counts by instance
- Message throughput by broker
- Error rates across different application services
- Request volume by API endpoint

## Metric aggregations

Metric aggregations summarize collected metric data over a selected time range, making it easier to analyze trends, compare historical performance, and identify usage patterns across your infrastructure and applications.

The Observability module applies aggregations to the raw metric data points collected during the selected time period. The aggregation method you select determines how the data points are combined and displayed in the Metrics dashboard.

Use metric aggregations to:

- Analyze short-term and long-term performance trends.
- Compare historical performance across time periods.
- Identify peak usage patterns and resource consumption spikes.
- Detect anomalies and deviations from baseline behavior.
- Support capacity planning and infrastructure optimization decisions.

### Average

The **Average \(Avg\)** aggregation displays the mean value of the metric across all data points collected during the selected time period. Use it to understand the typical behavior of a metric over time and identify deviations from normal operating conditions.

Use average aggregation for the following scenarios:

- Understanding baseline CPU or memory utilization
- Identifying consistent performance trends over time
- Comparing average response times across services
- Detecting gradual performance degradation

**Example:** Average CPU utilization over the last 24 hours.

### Minimum

The **Minimum \(Min\)** aggregation displays the lowest recorded value of the metric during the selected time period. Use it to identify the lowest resource utilization or activity levels and understand the best-case performance of a system component.

Use minimum aggregation for the following scenarios:

- Identifying periods of lowest resource consumption
- Understanding baseline performance thresholds
- Detecting underutilized resources
- Analyzing off-peak system behavior

**Example:** Minimum memory usage during a monitoring interval.

### Maximum

The **Maximum \(Max\)** aggregation displays the highest recorded value of the metric during the selected time period. Use it to identify peak resource consumption or activity and detect potential capacity or performance risks before they impact users.

Use maximum aggregation for the following scenarios:

- Identifying peak resource utilization periods
- Detecting traffic spikes and load surges
- Monitoring maximum response times during high-traffic events
- Capacity planning based on peak consumption patterns

**Example:** Maximum network throughput during peak traffic hours.

### Sum

The **Sum** aggregation displays the total accumulated value of all data points collected during the selected time period. This aggregation is most commonly used with counter metrics to measure total activity over a time range.

Use sum aggregation for the following scenarios:

- Measuring total request volume over a time period
- Tracking total error counts across services
- Calculating total message throughput across brokers
- Summarizing total database transactions within a window

**Example:** Total requests processed during the last hour.

### Count

The **Count** aggregation displays the total number of metric data samples collected during the selected time period. Count aggregation differs from sum aggregation because it counts the number of observations rather than the accumulated value of those observations.

Use count aggregation for the following scenarios:

- Measuring the number of response time samples collected
- Counting the frequency of metric data collection intervals
- Verifying data completeness during monitoring intervals
- Identifying gaps in metric data collection

**Example:** Number of response time measurements collected during a monitoring window.
